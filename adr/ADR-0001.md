# ADR-0001: Separate Tutor Brain policy from reasoning engines

**Status:** Accepted — 2026-07-19

## Context

LLM providers differ in availability, capability, price, latency, and behaviour, and they
change on their own schedule. A tutoring product has a multi-year relationship with a student;
a model has a support window measured in months.

## Problem

If tutoring policy lives in provider-specific system prompts, the product inherits the
provider's lifecycle. Changing models means rewriting behaviour, revalidating quality, and
migrating a student's history out of a vendor's conversation format. Policy expressed in prose
is also unauditable: there is no way to prove what rule was applied to a given decision.

## Decision

The Tutor Brain owns schemas, deterministic decisions, workflow transitions, and validation.
Reasoning providers are reached through a **capability-based adapter**, and prompt files are
provider-neutral.

No business rule may depend on the identity of the reasoning engine. Prompts declare the
capabilities they require — structured output, tool calling, context limit, citation support —
and a dispatcher selects any eligible engine.

## Alternatives Considered

| Alternative | Why rejected |
| --- | --- |
| Single-provider system prompt | Fastest to build, but couples product lifespan to the provider and makes policy unauditable. |
| Framework-level abstraction library | Trades provider lock-in for framework lock-in, and imports an execution model this repository deliberately does not specify. |
| Fine-tuned model carrying the policy | Policy becomes opaque weights: not reviewable, not diffable, not correctable without retraining. |
| Provider-neutral prompts with no capability contract | Portable in name only; a prompt requiring structured output fails silently on an engine that lacks it. |

## Tradeoffs

**Accepted cost:** adapter implementation and maintenance per provider; a capability
negotiation layer; output quality that varies by engine and requires per-engine evaluation;
inability to use a provider's most differentiated proprietary features.

**Gained:** providers can be switched, compared, or used selectively per action type without
migrating student state or rewriting policy. Every decision has a reviewable rule behind it.

## Consequences

- Prompt contracts are written as API specifications
  ([Prompt Architecture](../docs/09%20Prompt%20Architecture.md)).
- Boundary B4 in [architecture.md](../architecture/architecture.md) is a hard trust boundary.
- Adding a provider is an adapter change, never a specification change.
- Per-engine quality benchmarking becomes a required operational practice, not an optional one.

## Future Considerations

- Capability negotiation may need a richer type than a flat capability set as providers expose
  more heterogeneous features.
- Per-action-type engine routing (cheap engine for `draft_check`, strong engine for
  `evaluate_answer`) is anticipated in Phase 5 and does not require revisiting this decision.
- If a provider offers durable server-side state, this ADR forbids depending on it; state
  remains ours.
