# ADR-0004: Establish a single authority hierarchy for component conflicts

**Status:** Accepted — 2026-07-19

## Context

Four engines and two stores act on overlapping state. In normal operation they compose
cleanly, but several pairs can produce genuinely incompatible outputs from valid inputs:
planning and revision competing for the same minutes, evaluation implying a mastery change the
Student Model has not computed, two memory records asserting contradictory facts.

Phase 1 specified each component's responsibility but did not state which one wins.

## Problem

Unresolved conflicts do not stay unresolved — they get settled implicitly by whichever
component happens to run last, or by a tie-breaker added locally during implementation. Both
outcomes place real policy in code that no specification describes, which is precisely the
failure mode [ADR-0001](ADR-0001.md) exists to prevent.

A conflict that is resolvable two different ways is a specification defect, not an
implementation detail.

## Decision

Conflict precedence is specified centrally in the
[Tutor Constitution](../docs/01%20Tutor%20Constitution.md), in three linked parts:

1. **Authority hierarchy (§3)** — a seven-level ordering from Constitution down to model
   output, with student authority scoped explicitly.
2. **Conflict resolution table (§5)** — nine named component-pair conflicts, each with one
   stated resolution.
3. **Policy parameters (§9)** — every threshold a resolution depends on, declared once and
   referenced by name.

A conflict not covered by §5 SHALL be escalated as a specification defect and closed by
amending §5 — never by adding compensating logic in an implementation.

## Alternatives Considered

| Alternative | Why rejected |
| --- | --- |
| Document precedence in each engine's own spec | Each engine states its own case; two documents can claim precedence and both look correct in isolation. |
| Resolve conflicts in the Orchestrator at runtime | Moves policy into the one component defined as holding none, and makes resolution unreviewable. |
| Priority scores instead of an explicit hierarchy | Scores compose unpredictably and hide the actual rule; two tunings produce different behaviour with no diff. |
| Escalate every conflict to the student | Correct in principle, exhausting in practice; the student is asked to arbitrate system-internal disagreements. |

## Tradeoffs

**Accepted cost:** the Constitution grows and becomes a required read; adding a component now
requires placing it in the hierarchy and enumerating its conflicts before it can be specified;
some resolutions are necessarily arbitrary and will need calibration against real usage.

**Gained:** every conflict has one documented answer, testable in isolation. Precedence is
diffable and reviewable. Implementations cannot introduce silent policy.

## Consequences

- [Constitution §5](../docs/01%20Tutor%20Constitution.md#5-conflict-resolution) is normative;
  engine documents reference rules C1–C9 and MUST NOT restate them.
- Dependency rule D1 in [architecture.md](../architecture/architecture.md#5-module-dependencies)
  follows directly: engines do not call each other, so conflicts surface at the Orchestrator
  where the table applies.
- [Extension Rules](../docs/01%20Tutor%20Constitution.md#10-extension-rules) require a new
  conflict to be added to §5 in the same change that introduces it.
- Thresholds are no longer restated across documents; §9 is the single source.

## Future Considerations

- The §5 table grows quadratically with component count. Beyond roughly a dozen components it
  may need grouping by boundary rather than by pair.
- C1's backlog threshold and C5's contradiction rule are the two resolutions most likely to
  need empirical calibration once outcome data exists (Phase 6).
- If student-facing conflict explanation is added, §5 becomes the natural source for the
  user-visible rationale.
