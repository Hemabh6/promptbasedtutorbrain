# ADR-0003: Validate structured outputs before state mutation

**Status:** Accepted — 2026-07-19

## Context

Every durable artifact in this system — a plan, an evaluation, a memory record — originates as
generated content. Generated output can be malformed, internally inconsistent, silently
truncated, or shaped by an injection embedded in student text or a retrieved source.

## Problem

Persisting model output directly corrupts the student record in ways that are hard to detect
and harder to reverse. A fabricated score, a plan that exceeds capacity, or a memory record
without provenance all look like ordinary data once written. Under
[ADR-0002](ADR-0002.md), a bad write also contaminates every view derived from it.

## Decision

All generated artifacts pass **schema validation, semantic checks, and workflow
authorisation** before persistence.

Failed output is retryable up to `prompt.validation_retry_max` with machine-readable errors,
and is then rejected. A write either completes fully or leaves state unchanged — partial
commits are prohibited.

## Alternatives Considered

| Alternative | Why rejected |
| --- | --- |
| Trust provider structured-output modes | Guarantees syntax, not semantics. A well-formed plan can still exceed capacity or drop a due item. |
| Validate on read instead of write | Defers the failure to the worst moment and leaves invalid data resident and replicable. |
| Best-effort repair of malformed output | Repair invents content; the repaired artifact is indistinguishable from a genuine one. |
| Human review of every write | Correct but unusable at session cadence; would make the tutor synchronous on a person. |

## Tradeoffs

**Accepted cost:** parsers, a repair-and-retry path, and actionable validation error messages
must be built and maintained; strict validation raises the visible failure rate, especially on
weaker engines; schema changes require migration discipline.

**Gained:** transactional integrity, provider independence, and a hard guarantee that a
successful prompt injection cannot by itself mutate durable state.

## Consequences

- `additionalProperties: false` throughout `schemas/`; undeclared fields fail validation rather
  than passing silently.
- Semantic checks — capacity, prerequisite satisfaction, due-set reservation, arithmetic — are
  application responsibilities and cannot be delegated to the schema.
- The Orchestrator, not any engine, owns the validate-then-commit sequence
  ([architecture.md §3](../architecture/architecture.md#3-execution-flow)).
- Validation failure is a first-class outcome with a defined behaviour, not an exception path.

## Future Considerations

- Retry budget and repair strategy may need per-engine tuning as capability profiles diverge.
- Semantic checks currently live in prose across engine documents; a machine-readable rule
  format may be justified once an implementation exists.
- Schema versioning will require a migration framework before the first breaking change ships.
